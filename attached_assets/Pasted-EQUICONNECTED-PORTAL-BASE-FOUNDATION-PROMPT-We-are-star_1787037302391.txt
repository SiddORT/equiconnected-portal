EQUICONNECTED PORTAL — BASE FOUNDATION PROMPT

We are starting a completely NEW EquiConnected Portal application.

IMPORTANT:
This is a separate project from the existing EquiConnected Coming Soon website.

The existing public/Coming Soon application uses React + Node/Express.
DO NOT modify, import, replace, or depend on that application's runtime, code, deployment, or dependencies.

This new application will be the foundation for the future EquiConnected platform.

==================================================
1. TECHNOLOGY STACK
==================================================

Frontend:
- React
- TypeScript
- Modern component-based architecture
- Responsive/mobile-first UI

Backend:
- Python
- FastAPI
- REST API
- Pydantic for request/response validation

Database:
- PostgreSQL
- SQLAlchemy ORM
- Alembic migrations

Authentication:
- Secure authentication architecture
- Password hashing using a strong password hashing algorithm such as Argon2id
- Secure authentication/session or token strategy
- Protected routes
- Role-based access control foundation

Do NOT use JSON files, SQLite, browser local storage, or in-memory storage as the application database.

==================================================
6. DATABASE ARCHITECTURE
==================================================

PostgreSQL is the source of truth.

Design a normalized relational schema.

DO NOT store application entities as large JSON blobs.

DO NOT store relational data inside JSON strings.

DO NOT create a generic table such as:

data:
{
  "hospital": ...,
  "user": ...,
  "visitor": ...
}

Instead use proper relational tables with:

- Primary keys
- Foreign keys
- Unique constraints
- NOT NULL constraints where appropriate
- Indexes
- Proper data types
- Created/updated timestamps
- Referential integrity

Use normalized relational design.

If an entity has a one-to-many relationship, create the appropriate related table.

If an entity has a many-to-many relationship, create a proper junction/association table.

Use PostgreSQL relationships and foreign keys rather than duplicating data.

Future entities will include concepts such as:

- Users
- Roles
- Hospitals
- Hospital users
- Visitors
- Invitations
- Sessions/authentication records
- Audit logs

But ONLY implement the tables actually required for the current foundation.

Do not prematurely create large amounts of unused schema.

==================================================
7. DATA SECURITY
==================================================

Security is a core requirement.

Passwords:
- NEVER encrypt passwords for storage.
- Hash passwords using Argon2id or another modern, strong password hashing algorithm.
- Passwords must never be stored in plaintext.
- Passwords must never be logged.

Sensitive recoverable data:
- Encrypt sensitive personal data at rest where appropriate.
- Encryption keys must come from environment/secret management.
- NEVER hard-code encryption keys.
- NEVER commit secrets to Git.
- Never expose encryption keys to the React frontend.

Secrets:
- Database credentials come from environment variables/secrets.
- API secrets come from environment variables/secrets.
- Encryption keys come from environment variables/secrets.
- No credentials or secrets in source code.

API:
- Validate all input on the backend.
- Never trust frontend validation alone.
- Use appropriate authentication and authorization checks.
- Never return passwords or password hashes through API responses.
- Avoid exposing unnecessary personal/sensitive information.

==================================================
8. NO HARDCODED APPLICATION DATA
==================================================

Do NOT hard-code application data into React components.

Bad:

const hospitals = [
  { name: "Hospital A" },
  { name: "Hospital B" }
];

Good:

React → FastAPI → PostgreSQL

Static UI configuration is acceptable.

Application/business data must come from the backend/database.

This applies to:

- Users
- Hospitals
- Visitors
- Invitations
- Dashboard metrics
- Roles
- Statuses
- Records
- Lists
- Search results

==================================================
9. API ARCHITECTURE
==================================================

Create a clean FastAPI architecture.

Organize code into logical modules such as:

backend/
  app/
    main.py
    core/
    api/
    models/
    schemas/
    services/
    repositories/
    db/
    auth/

Keep responsibilities separated.

Routes/controllers should not contain large amounts of business logic.

Use service-layer functions for business logic.

Use repository/data-access patterns where appropriate.

Use Pydantic schemas for API boundaries.

Keep database models separate from API response schemas.

==================================================
10. FRONTEND ARCHITECTURE
==================================================

Use a scalable React architecture.

Organize frontend code logically, for example:

src/
  app/
  components/
  layouts/
  pages/
  features/
  hooks/
  services/
  api/
  types/
  utils/
  styles/

Use feature-based organization where it improves maintainability.

Avoid one giant App.tsx.

Avoid giant components.

Keep components small and reusable.

Do not duplicate API calls or business logic across pages.

Create shared API/client utilities.

Centralize authentication state.

==================================================
11. ERROR / LOADING / EMPTY STATES
==================================================

Every data-driven screen should account for:

- Loading
- Success
- Empty
- Error
- Unauthorized
- Forbidden

Do not leave blank screens when an API request fails.

Display useful user-friendly messages.

Do not expose raw backend stack traces to users.

Log technical errors on the backend appropriately.

Frontend validation:
- Good UX

16. DATABASE MIGRATIONS
==================================================

All schema changes must use migrations.

Do NOT manually modify production database tables as part of normal development.

Use Alembic migrations.

Migration workflow:

Model change
→ migration
→ review
→ apply

The database must be reproducible from migrations.

18. CORS / SECURITY
==================================================

Configure CORS through environment/configuration.

Do not use unrestricted CORS in production unless there is a specific reason.
