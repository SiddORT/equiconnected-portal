EQUICONNECTED PORTAL — PHASE 3
SPECIALIZATION MASTER

Implement ONLY the Specialization Master module in the Admin Portal.

Do not implement Hospital, Clinic, Doctor, Visitor, Reviews, Invitations, or any other business module yet.

The purpose of this phase is to create a clean, reusable master-data CRUD pattern that we can use for future Admin masters.

==================================================
1. ROUTE
==================================================

Create:

/admin/specializations

The route must be protected and accessible only to authenticated Admin users.

Add "Specializations" to the Admin sidebar/navigation.

==================================================
2. DATABASE
==================================================

Create a PostgreSQL table for specializations using the existing SQLAlchemy + Alembic architecture.

Suggested fields:

specializations
- id
- name
- description
- is_active
- created_at
- updated_at

Use the appropriate PostgreSQL data types.

Requirements:

- Primary key
- Unique constraint on specialization name
- Appropriate indexes
- NOT NULL where appropriate
- Created/updated timestamps
- Database-level integrity constraints

Do NOT store specializations as JSON.

Do NOT store a list of specialization names inside another table.

Specializations must be proper relational records because hospitals, clinics and doctors will later reference them.

==================================================
3. MIGRATION
==================================================

Create an Alembic migration for the specialization table.

Do not manually modify the database schema.

The migration must be safe and reproducible.

==================================================
4. ADMIN FEATURES
==================================================

Admin should be able to:

- View specializations
- Add specialization
- Edit specialization
- Activate specialization
- Deactivate specialization
- Search specializations
- Filter by active/inactive status
- Sort where appropriate
- Paginate results if needed

Do not add unnecessary functionality yet.

==================================================
5. CREATE SPECIALIZATION
==================================================

Provide an Admin UI for adding a specialization.

Fields:

- Name
- Description
- Active/inactive state where appropriate

Validation:

- Name is required
- Name must be trimmed
- Name must not be empty
- Duplicate names must be rejected
- Backend validation is mandatory
- Frontend validation is for user experience only

Do not rely on frontend validation to enforce uniqueness.

The database unique constraint must also protect against duplicate records.

==================================================
6. EDIT SPECIALIZATION
==================================================

Admin can edit:

- Name
- Description
- Active/inactive state

When changing the name:

- Validate uniqueness
- Handle database constraint errors cleanly
- Never expose raw database errors to the user

==================================================
7. ACTIVE / INACTIVE
==================================================

Do NOT delete specializations as the normal Admin action.

Use:

is_active

When a specialization is deactivated:

- Existing relationships should remain intact
- The record remains in PostgreSQL
- It should not normally be selectable for new provider associations
- Existing provider relationships should not be silently deleted

The exact behavior for existing providers will be defined when we build Provider Management.

==================================================
8. UI
==================================================

Create a polished Admin specialization management page using the existing EquiConnected design system.

Page structure:

- Page title
- Description
- Add Specialization button
- Search
- Active/Inactive filter
- Specialization table
- Status indicator
- Edit action
- Activate/deactivate action
- Pagination where appropriate

Use the reusable components created in the foundation.

Do NOT create duplicate UI components specifically for this page if an existing reusable component can be used.

==================================================
9. FORM UX
==================================================

Create a reusable specialization form component.

The same form component should support:

- Create
- Edit

Handle:

- Loading
- Validation errors
- API errors
- Success state
- Cancel
- Unsaved changes appropriately if applicable

Do not duplicate create/edit form logic.

==================================================
10. API
==================================================

Create clean FastAPI endpoints for:

GET    /api/admin/specializations
POST   /api/admin/specializations
GET    /api/admin/specializations/{id}
PATCH  /api/admin/specializations/{id}
PATCH  /api/admin/specializations/{id}/status

Use appropriate HTTP status codes.

All endpoints must require Admin authorization.

Use Pydantic schemas for:

- Create request
- Update request
- Response

Do not expose database/ORM objects directly as API contracts.

==================================================
11. ARCHITECTURE
==================================================

Follow the existing project architecture.

Keep responsibilities separated:

API routes
→ services
→ repositories/data access
→ SQLAlchemy models

Do not put business logic directly into React components.

Do not put large amounts of business logic directly inside FastAPI route handlers.

Create reusable patterns that can later be applied to:

- Facilities
- Services
- Provider types
- Other master data

But DO NOT implement those masters now.

==================================================
12. SEARCH / FILTER / PAGINATION
==================================================

Search should operate through the backend/database.

Do NOT download the entire specialization table to React and filter it in JavaScript.

Support:

- Search by name
- Active/inactive filter
- Pagination

Use appropriate database queries and indexes.

Keep the API scalable for a larger dataset.

==================================================
13. NO HARDCODED DATA
==================================================

Do not hard-code specialization names such as:

Cardiology
Neurology
Orthopedics
etc.

The database must be the source of truth.

Do not create fake/demo specializations.

If the database is empty, display a proper empty state.

==================================================
14. SECURITY
==================================================

Only authenticated Admin users can manage specializations.

Verify authorization on the backend.

Do not rely only on frontend route protection.

Validate all input.

Do not expose stack traces or raw database errors to users.

Do not log secrets or sensitive authentication information.

==================================================
15. TESTING
==================================================

Add tests covering:

- Admin can list specializations
- Non-admin cannot access the endpoints
- Unauthenticated users cannot access the endpoints
- Create specialization
- Required name validation
- Duplicate specialization prevention
- Edit specialization
- Activate specialization
- Deactivate specialization
- Search
- Active/inactive filtering
- Pagination
- Database constraints

Test both successful and failure cases.

==================================================
16. DESIGN FOR FUTURE RELATIONSHIPS
==================================================

This is important:

Hospitals, clinics and doctors will later be able to have MULTIPLE specializations.

Therefore the specialization table must be designed as an independent master entity.

Later we will create proper many-to-many relationships such as:

hospital_specializations
clinic_specializations
doctor_specializations

Do NOT create those relationship tables in this phase.

Do NOT add hospital/clinic/doctor foreign keys yet.

==================================================
17. DOCUMENTATION
==================================================

Update the project documentation with:

- New route
- Database table
- Migration
- API endpoints
- Validation rules
- Admin permissions
- How to run the migration
- How to run tests

==================================================
18. COMPLETION CRITERIA
==================================================

Phase 3 is complete only when:

1. Admin can open /admin/specializations
2. Admin can create a specialization
3. Admin can edit it
4. Admin can deactivate it
5. Admin can reactivate it
6. Duplicate names are prevented
7. Search works through the API/database
8. Active/inactive filtering works
9. Pagination works if applicable
10. Unauthorized users cannot access it
11. Database migration works
12. Tests pass
13. No fake/hard-coded specialization data exists
14. Existing Admin authentication continues working
15. Existing Admin dashboard continues working

At completion, report:

1. Files created/changed
2. Database table created
3. Migration created
4. API endpoints
5. Frontend route
6. Components created/reused
7. Tests added
8. Commands used to migrate/test
9. Any architectural decisions that require approval

IMPORTANT:

Do not proceed to Hospital/Clinic/Doctor implementation after completing this task.

Stop after Specialization Master is complete.
