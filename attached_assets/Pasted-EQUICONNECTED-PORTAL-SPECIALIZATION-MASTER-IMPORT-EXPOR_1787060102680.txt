EQUICONNECTED PORTAL — SPECIALIZATION MASTER
IMPORT / EXPORT EXTENSION

Extend the existing Specialization Master module with CSV Import and Export.

IMPORTANT:

This is an extension of the existing Specialization Master.

Do NOT implement:

- Hospital import/export
- Clinic import/export
- Doctor import/export
- Visitor import/export
- Activity Logs
- Hospital invitations
- Provider management

Those will be handled separately.

==================================================
1. EXPORT
==================================================

Add an Export action to:

/admin/specializations

The Admin must be able to export specialization data as CSV.

Export should support:

- Export all specializations
- Export the currently filtered result set

If filters/search are active, the export should respect the selected filters.

Examples:

- Export only active specializations
- Export only inactive specializations
- Export current search results

Do not export data that is not visible/authorized to the Admin.

==================================================
2. CSV FORMAT
==================================================

Use UTF-8 encoded CSV.

Export columns should be:

- ID
- Name
- Description
- Status
- Created At
- Updated At

Use human-readable status values.

Do not expose internal database information unnecessarily.

Use consistent date/time formatting.

The CSV must open correctly in common spreadsheet applications.

Do not generate JSON for the export.

==================================================
3. EXPORT IMPLEMENTATION
==================================================

Export must be generated from the backend/database.

Do NOT:

- Load the entire database table into React
- Generate the CSV entirely in the browser
- Hard-code CSV data

React should request the export from FastAPI.

The backend should generate the CSV using actual PostgreSQL data.

Use streaming or an appropriately memory-efficient implementation if the dataset becomes large.

Return the correct:

Content-Type

and

Content-Disposition

headers.

Use a safe filename such as:

equiconnected-specializations-YYYY-MM-DD.csv

==================================================
4. IMPORT
==================================================

Add an Import action to:

/admin/specializations

The Admin should be able to upload a CSV file.

Recommended flow:

Upload
  ↓
Parse
  ↓
Validate
  ↓
Preview
  ↓
Admin confirms
  ↓
Import
  ↓
Result summary

Do NOT immediately insert rows as soon as the file is uploaded.

The Admin must be able to review the import before committing it.

==================================================
5. IMPORT FILE VALIDATION
==================================================

Accept CSV only.

Validate:

- File extension
- MIME type where available
- File size
- Encoding
- CSV structure
- Required headers

Reject invalid files with a clear error.

Do not trust the filename or MIME type alone.

The backend must validate the actual file contents.

==================================================
6. IMPORT HEADERS
==================================================

The import template should support:

Name
Description
Status

ID, Created At and Updated At should NOT be required for new imports.

Do not allow the CSV to directly manipulate:

- Database primary keys
- Created timestamps
- Updated timestamps

Those are controlled by the application/database.

Provide an optional downloadable import template:

equiconnected-specializations-template.csv

The template should contain the correct headers and example formatting guidance where appropriate.

Do not put fake business records into the template.

==================================================
7. DATA NORMALIZATION
==================================================

During import:

- Trim leading/trailing whitespace
- Normalize empty strings
- Validate required fields
- Normalize status values
- Handle blank descriptions as NULL/empty according to the existing schema
- Normalize specialization name consistently for duplicate detection

Do not silently alter meaningful user data.

==================================================
8. REQUIRED FIELD
==================================================

Name is required.

If Name is missing:

- Reject that row
- Show the row number
- Show the reason

Example:

Row 7:
Name is required.

==================================================
9. DUPLICATE HANDLING
==================================================

Duplicate specializations must NOT be silently inserted.

For this module, use:

DUPLICATE → SKIP + REPORT

Do NOT automatically overwrite existing specialization records.

Do NOT automatically update an existing specialization simply because the name matches.

Duplicate detection should be performed using the same normalization/uniqueness rules as the database.

Example result:

Imported: 18
Skipped: 3
Errors: 2

Skipped:
Row 4 — Cardiology already exists
Row 9 — Neurology already exists

==================================================
10. IMPORT PREVIEW
==================================================

Before committing the import, display a preview.

The preview should show:

- Total rows
- Valid rows
- Duplicate rows
- Invalid rows

And a table containing:

- Row number
- Name
- Description
- Status
- Validation result
- Error/reason where applicable

Use the existing reusable DataTable.

Do not create a separate custom table implementation.

==================================================
11. IMPORT CONFIRMATION
==================================================

Only valid, non-duplicate rows should be eligible for import.

The Admin must explicitly confirm:

"Import X specializations"

before database changes are committed.

If there are invalid/duplicate rows, clearly explain that they will not be imported.

Do not make the Admin assume that all uploaded rows were accepted.

==================================================
12. TRANSACTION SAFETY
==================================================

The final database import must be transaction-safe.

Do not leave the database in a partially corrupted state.

Use an appropriate transaction strategy.

If an unexpected database error occurs during the commit:

- Roll back appropriately
- Do not report a successful import
- Show a user-friendly error
- Log technical details server-side without exposing sensitive information

Duplicate rows should be handled intentionally rather than causing an uncontrolled transaction failure.

==================================================
13. IMPORT RESULT
==================================================

After import, show a clear summary:

Total rows:
25

Imported:
18

Skipped:
5

Errors:
2

Provide row-level details for skipped/error rows.

Allow the Admin to download an error report if appropriate.

The error report should be CSV.

Example:

Row,Name,Reason
4,Cardiology,Duplicate specialization
9,,Name is required

Do not include sensitive information unnecessarily.

==================================================
14. ACTIVE / INACTIVE STATUS
==================================================

Import should support the Status column.

Accept controlled values such as:

ACTIVE
INACTIVE

Also support the human-readable equivalents used by the UI if appropriate.

Normalize them on the backend.

Reject unsupported values.

Example:

Row 5:
Invalid status: "ARCHIVED"

Do not silently convert invalid status values.

==================================================
15. SECURITY
==================================================

Only authenticated Admin users can import/export specializations.

Backend authorization is mandatory.

Do not rely only on hiding buttons in React.

Protect against:

- Oversized files
- Malformed CSV
- Unexpected columns
- Malicious input
- Formula injection where applicable
- CSV parsing abuse

Be especially careful with values beginning with spreadsheet formula characters such as:

=
+
-
@

Do not create an export that could unintentionally execute spreadsheet formulas when opened in spreadsheet software.

==================================================
16. IMPORT API
==================================================

Create clean FastAPI endpoints.

For example:

GET
/api/admin/specializations/export

POST
/api/admin/specializations/import/preview

POST
/api/admin/specializations/import

GET
/api/admin/specializations/import/template

Use appropriate HTTP status codes.

The preview endpoint must NOT permanently modify the database.

The final import endpoint performs the confirmed database operation.

==================================================
17. FRONTEND UI
==================================================

On:

/admin/specializations

Add:

- Import button
- Export button

Import flow can use a modal/dialog or dedicated reusable import interface.

Reuse existing:

- Modal/Dialog
- File upload
- DataTable
- Button
- Alert
- Badge
- Loading state
- Error state
- Empty state
- Confirmation dialog

Do NOT create duplicate UI components.

==================================================
18. REUSABLE IMPORT COMPONENT
==================================================

Create the import UI in a reusable way.

The architecture should eventually allow us to reuse the same import framework for:

- Providers
- Doctors
- Users
- Other master data

However, ONLY implement the specialization import now.

Do not create fake implementations for future modules.

The reusable component should allow future configuration for:

- Required columns
- Column mapping
- Validation
- Preview columns
- Duplicate strategy
- Import endpoint

==================================================
19. REUSABLE EXPORT PATTERN
==================================================

Similarly, create the export mechanism in a reusable/configurable way where practical.

Future modules should be able to define:

- Export columns
- Column labels
- Formatting
- Filters
- Filename

Do not duplicate export logic for every future module.

==================================================
20. DATABASE INTEGRITY
==================================================

The existing specialization database constraints remain the final protection against duplicate data.

Import logic must not bypass:

- Unique constraints
- NOT NULL constraints
- Other existing database constraints

Do not remove or weaken existing constraints to make imports easier.

==================================================
21. TESTING
==================================================

Add tests for:

EXPORT:

- Export all specializations
- Export filtered results
- Correct CSV headers
- Correct UTF-8 output
- Correct status formatting
- Correct content type
- Correct filename

IMPORT:

- Valid CSV
- Missing required column
- Missing name
- Duplicate specialization
- Invalid status
- Whitespace normalization
- Empty description
- Malformed CSV
- Oversized file
- Unauthorized import
- Preview does not modify database
- Confirmed import modifies database
- Transaction rollback
- Partial failure handling
- Error report generation

Security:

- Non-admin cannot import
- Non-admin cannot export

==================================================
22. NO HARDCODED BUSINESS DATA
==================================================

Do not hard-code specialization names.

Do not use demo records to make import/export appear functional.

All exported records must come from PostgreSQL.

All imported records must be persisted in PostgreSQL.

==================================================
23. ACTIVITY LOG PREPARATION
==================================================

IMPORTANT:

We are intentionally implementing the centralized Activity Log system later, after the major modules are complete.

Therefore:

DO NOT create the final Activity Log module now.

However, structure the Import/Export service so that the final Activity Logging system can later record:

- Specialization import
- Specialization export
- Number of rows imported
- Number skipped
- Number failed
- Admin/user who performed the operation
- Timestamp

Do not create a duplicate temporary activity-log system.

==================================================
24. COMPLETION CRITERIA
==================================================

This phase is complete when:

1. Admin can export all specializations
2. Admin can export filtered specializations
3. Admin can download the import template
4. Admin can upload a CSV
5. CSV is validated
6. Admin can preview the import
7. Duplicate rows are detected
8. Invalid rows are reported
9. Admin must confirm before importing
10. Valid rows are imported
11. Duplicate rows are skipped
12. Invalid rows are skipped
13. Database remains transaction-safe
14. Error report can be generated
15. Unauthorized users cannot import/export
16. Existing Specialization CRUD still works
17. Existing DataTable/UI components are reused
18. Tests pass
19. No JSON storage is introduced
20. No hard-coded specialization data is introduced
21. Activity logging is NOT duplicated or prematurely implemented

At completion, report:

1. Files/modules created or changed
2. API endpoints
3. Import CSV format
4. Export CSV format
5. Validation rules
6. Duplicate strategy
7. Transaction strategy
8. Reusable components created/reused
9. Tests added
10. Migration changes, if any
11. Commands to test import/export
12. Any decisions requiring approval

STOP after completing Specialization Import/Export.
Do not proceed to Provider Management automatically.
