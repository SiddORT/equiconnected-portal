EQUICONNECTED PORTAL — PHASE 6
DOCTOR MANAGEMENT + DOCTOR/PROVIDER RELATIONSHIPS

Implement Doctor Management on top of the existing Provider foundation from Phases 4 and 5.

IMPORTANT:

Before making changes, inspect the existing implementation from Phases 3, 4 and 5, including:

- Provider schema
- Provider types
- Provider status/publication status
- Visit stability
- Specialization relationships
- Location model
- Photo/media model
- Existing DataTable
- Existing reusable form components
- Existing API/service/repository architecture
- Existing authentication/authorization

EXTEND the existing architecture.

Do NOT create duplicate Provider, Specialization, Photo, Location, DataTable, or authentication systems.

==================================================
1. CORE REQUIREMENT
==================================================

A Doctor is an independent healthcare provider.

A Doctor may:

1. Exist independently as an individual Doctor provider.
2. Be added/managed by an Admin.
3. Be added by a Hospital.
4. Be added by a Clinic.
5. Be associated with multiple Hospitals and/or Clinics.
6. Eventually manage their own profile through a Doctor account.

Do NOT make a Doctor permanently owned by one Hospital or Clinic.

The Doctor profile must exist independently from the organization relationships.

Example:

Doctor:
Dr. John Smith

Relationships:

Dr. John Smith
 ├── ABC Hospital
 ├── XYZ Hospital
 └── City Clinic

==================================================
2. DOCTOR PROFILE VS ORGANIZATION RELATIONSHIP
==================================================

This distinction is critical.

Separate:

A. Global Doctor Profile

from:

B. Doctor ↔ Hospital/Clinic relationship

The Doctor Profile represents information about the individual.

The relationship represents the doctor's association with a specific organization.

Do not duplicate global Doctor information into every Hospital/Clinic record.

==================================================
3. GLOBAL DOCTOR PROFILE
==================================================

The Doctor profile should support information such as:

- Name
- Professional title
- Biography
- Qualifications
- Experience
- Specializations
- Profile photo
- Other professional information
- Visit stability
- Status
- Publication status

Use the existing Provider foundation wherever possible.

Do not duplicate Provider fields unnecessarily.

Do not store doctor profile information as a JSON blob.

Use proper relational columns/tables.

==================================================
4. PROFESSIONAL TITLE
==================================================

Support a professional title such as:

- Dr.
- Professor
- Consultant
- Specialist
- Surgeon

Do not hard-code a fixed list unless the existing business requirements require one.

Design this so it can remain a text/value initially and become a master later if required.

==================================================
5. BIOGRAPHY
==================================================

Allow a Doctor to have a professional biography.

The biography should be editable through the appropriate authorized workflow.

Use a normal text column.

Do NOT store biography content as JSON.

==================================================
6. QUALIFICATIONS
==================================================

Support Doctor qualifications.

Examples could include:

- Medical degree
- Specialist qualification
- Fellowship
- Certification

Do not hard-code specific qualification types.

If multiple qualifications need to be stored independently, use a proper relational structure rather than a JSON array.

The design should allow future expansion.

==================================================
7. EXPERIENCE
==================================================

Support professional experience.

The system should allow appropriate information such as:

- Years of experience
- Experience description
- Previous professional experience where applicable

Do not invent unnecessary mandatory fields.

Keep uncertain fields optional.

==================================================
8. SPECIALIZATIONS
==================================================

Doctors can have multiple specializations.

Use the existing Specialization Master.

Do NOT create another specialization table.

Example:

Dr. John Smith
 ├── Cardiology
 ├── Internal Medicine
 └── Preventive Medicine

Use the existing Provider ↔ Specialization architecture where appropriate.

Prevent duplicate relationships.

Only active specializations should normally be selectable for new assignments.

==================================================
9. VISIT STABILITY
==================================================

Reuse the existing Provider Visit Stability field.

Doctor supports:

- STABLE_VISIT
- NOT_STABLE_VISIT

Do NOT create a separate Doctor-specific stability field.

This remains a provider/business classification and is not patient medical information.

==================================================
10. DOCTOR ↔ HOSPITAL/CLINIC
==================================================

A Doctor can be associated with multiple Hospitals and Clinics.

Example:

Doctor
 ├── Hospital A
 ├── Hospital B
 └── Clinic C

Hospital A
 ├── Doctor 1
 ├── Doctor 2
 └── Doctor 3

Use a proper many-to-many relationship.

Create an appropriate junction table.

The relationship should support at least:

- doctor/provider_id
- organization/provider_id
- relationship status
- is_primary
- created_at
- updated_at

Only these Provider types may be organizations in this relationship:

- HOSPITAL
- CLINIC

A Doctor must NOT be associated with another Doctor through this relationship.

==================================================
11. RELATIONSHIP STATUS
==================================================

Doctor status and Doctor ↔ Organization relationship status are separate concepts.

Example:

Doctor:
ACTIVE

Relationship:

Dr. Smith → ABC Hospital
ACTIVE

Dr. Smith → XYZ Clinic
INACTIVE

Deactivating one relationship must NOT deactivate the Doctor globally.

Removing one organization relationship must NOT delete the Doctor.

==================================================
12. PRIMARY ORGANIZATION
==================================================

Support an optional primary Hospital/Clinic relationship.

Example:

Dr. Smith

Primary:
ABC Hospital

Additional:
XYZ Hospital
City Clinic

A Doctor does not have to have a primary organization.

A Doctor may exist independently without any Hospital/Clinic relationship.

Ensure the primary relationship is handled safely and consistently.

==================================================
13. WHO CAN CREATE A DOCTOR
==================================================

The architecture must support three creation paths:

A. Admin creates Doctor

B. Hospital/Clinic creates Doctor

C. Individual Doctor is eventually able to create/claim/manage their own Doctor profile

IMPORTANT:

Hospital/Clinic user functionality is implemented in a later phase.

Therefore, in this phase:

- Build the data model and service architecture needed to support organization-created Doctors.
- Implement Admin Doctor creation/management now.
- Do NOT build the Hospital/Clinic Portal yet.
- Do NOT build Doctor Login yet.

The future account/permission system must be able to attach an authenticated organization user to the appropriate Provider.

==================================================
14. OWNERSHIP AND EDITING RULES
==================================================

Do NOT assume that a Hospital or Clinic can edit every field on a Doctor's global profile.

Future authorization must distinguish:

Global Doctor Profile
vs.
Organization-specific relationship information.

For example:

Global Doctor Profile may include:

- Name
- Professional title
- Biography
- Qualifications
- Experience
- Specializations
- Profile photo

Organization relationship may eventually include:

- Department
- Role within organization
- Relationship status
- Organization-specific information

Do NOT implement organization-specific editing permissions until Hospital/Clinic accounts are implemented.

However, design the data model so this distinction is preserved.
