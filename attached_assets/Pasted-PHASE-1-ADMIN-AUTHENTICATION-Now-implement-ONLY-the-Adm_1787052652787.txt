PHASE 1 — ADMIN AUTHENTICATION

Now implement ONLY the Admin Authentication flow.

Do not build Hospital Management, Hospital Registration, Hospital Invitations, Visitor Login, Reviews, Doctors, or any other business module yet.

The purpose of this phase is to create a secure, production-ready Admin authentication foundation that we will build on later.

==================================================
1. ROUTES
==================================================

Public:

/
 
Admin:

/admin
/admin/login
/admin/dashboard

Behavior:

- /admin/login → Admin login page
- /admin/dashboard → Protected Admin dashboard
- /admin → redirect to /admin/dashboard if authenticated
- /admin → redirect to /admin/login if unauthenticated

Do not create additional admin business pages yet.

==================================================
2. ADMIN LOGIN
==================================================

Create a polished EquiConnected Admin Login page.

Fields:

- Email
- Password

Include:

- Email validation
- Required-field validation
- Password visibility toggle
- Loading state
- Invalid credentials state
- Generic authentication error
- Accessible form labels
- Keyboard accessibility
- Responsive design
- EquiConnected centralized design system/theme

Do not hard-code credentials.

Do not create public Admin registration.

==================================================
3. ADMIN DATABASE
==================================================

Use PostgreSQL.

Create the minimum relational database structure required for Admin authentication.

Admin authentication must be based on the application's user/authentication architecture so that we can later support:

- Admin
- Hospital users
- Visitor users

Do not create hospital or visitor business tables yet.

At minimum the authentication model should support:

- id
- email
- password_hash
- role
- is_active
- created_at
- updated_at

Use:

- Primary keys
- Unique email constraint
- Appropriate indexes
- Proper PostgreSQL data types
- Database constraints

Do not store authentication records as JSON.

Do not store application data in JSON strings.

==================================================
4. PASSWORD SECURITY
==================================================

Passwords must NEVER be stored in plaintext.

Use Argon2id or another strong modern password hashing algorithm.

Never:

- Encrypt passwords for storage
- Store plaintext passwords
- Log passwords
- Return password hashes through an API
- Send password hashes to React

The backend must perform password verification.

==================================================
5. AUTHENTICATION
==================================================

Implement a secure authentication/session strategy appropriate for a React + FastAPI application.

The browser must not receive unnecessary sensitive authentication information.

Authentication must persist appropriately across page refreshes.

Implement:

- Login
- Authentication check
- Logout
- Protected admin routes

The backend must enforce authentication.

Frontend route protection alone is NOT sufficient.

==================================================
6. AUTHORIZATION
==================================================

Implement role-based authorization at the backend level.

For this phase:

role = admin

Only authenticated active Admin users can access:

/admin/dashboard

If a valid authenticated user does not have the admin role, return an appropriate authorization response.

Prepare the architecture so that future roles can be introduced without rewriting authentication.

Do not implement Hospital or Visitor permissions yet.

==================================================
7. INITIAL ADMIN ACCOUNT
==================================================

Create a secure admin setup/seed mechanism.

Requirements:

- No credentials hard-coded in source code
- Credentials supplied through environment variables or secure setup input
- Safe to run more than once
- Do not create duplicate admin accounts
- Password must be hashed before insertion
- Never print the password
- Never log the password

Document the exact command used to create the initial Admin.

==================================================
8. ADMIN DASHBOARD
==================================================

Create:

/admin/dashboard

For now, this is ONLY the Admin Portal shell.

Include:

- EquiConnected branding
- Sidebar/navigation foundation
- Header
- Current admin information
- Logout
- Main dashboard content area
- Proper empty state

Do NOT create fake:

- Hospital counts
- Visitor counts
- Doctor counts
- Review counts
- Invitations
- Activity

There is no business data yet.

The dashboard should look production-ready but remain intentionally minimal.

==================================================
9. REUSABLE COMPONENTS
==================================================

Use the existing centralized component/design system.

Do not create one-off UI components if a reusable component should exist.

At minimum use/reuse:

- Button
- Input
- Form
- Card
- Alert
- Loading state
- Empty state
- Modal/dialog if needed
- Layout
- Sidebar
- Header

Keep components small and reusable.

Do not create duplicated implementations of the same UI pattern.

==================================================
10. API
==================================================

Create clean FastAPI authentication endpoints.

At minimum provide endpoints for:

- Admin login
- Current authenticated user/session
- Logout

Use appropriate HTTP methods and status codes.

Validate all input with Pydantic.

Do not expose unnecessary user information.

Authentication/business logic should not be embedded directly inside route handlers.

Keep responsibilities separated between:

- API routes
- Schemas
- Authentication/security
- Services
- Database models
- Database access

==================================================
11. ERROR HANDLING
==================================================

Login failures should return a generic user-facing message.

Do not reveal:

- Whether an email exists
- Database errors
- Password verification details
- Internal stack traces

Backend logs may contain useful technical information but must never contain passwords, tokens, secrets, or encryption keys.

Handle:

- Invalid credentials
- Inactive account
- Missing fields
- Invalid email
- Expired/invalid authentication
- Unauthorized access
- Server errors

with appropriate responses.

==================================================
12. SECURITY
==================================================

Implement sensible protection against brute-force login attempts/rate abuse.

Configure:

- CORS
- Authentication security
- Secure cookie/token settings according to the chosen authentication approach
- Environment-based secrets
- Production-safe configuration

Never hard-code:

- Database passwords
- Authentication secrets
- Encryption keys
- API keys

Use environment variables/secrets.

==================================================
13. MIGRATIONS
==================================================

Use Alembic for all database schema changes.

Create the migration for the Admin authentication tables.

Do not manually modify the schema as part of normal application startup.

The database must be reproducible through migrations.

==================================================
14. TESTING
==================================================

Add tests for:

1. Admin creation
2. Successful login
3. Invalid password
4. Invalid email
5. Inactive admin
6. Authentication persistence
7. Logout
8. Protected dashboard
9. Unauthorized access
10. Non-admin role rejection
11. Duplicate admin prevention

The tests must use real application logic and appropriate test database handling.

Do not use fake success responses just to make tests pass.

==================================================
15. NO MOCK DATA
==================================================

Do not add fake users, hospitals, doctors, reviews, statistics, or dashboard data.

The only initial database record should be created through the documented Admin seed/setup process.

Update the README with:

- How to configure environment variables
- How to start PostgreSQL
- How to run migrations
- How to create the first Admin
- How to start FastAPI
- How to start React
- How to run tests

==================================================
17. COMPLETION CRITERIA
==================================================

Do not consider this phase complete until the following works end-to-end:

1. Start PostgreSQL
2. Run migrations
3. Create initial Admin
4. Start FastAPI
5. Start React
6. Open /admin/login
7. Login with the seeded Admin
8. Redirect to /admin/dashboard
9. Refresh the page and remain authenticated
10. Logout
11. Attempt to access /admin/dashboard while logged out
12. Confirm access is denied/redirected to login
13. Attempt invalid credentials
14. Confirm login fails securely
15. Run authentication tests successfully
